# 仓储管理系统 · 组合抄方案

> 目标：公司内部用。运营侧出单 → 后台收单 → 仓储接单 → 采购/备货 → 发货 → 状态回传运营。
> 原则：技术栈尽量轻、尽量好改；能抄的抄，抄不到的自己写。

---

## 一、技术栈选型

### 主推方案

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | **Python 3.12 + FastAPI** | 单文件即可起服务，无重框架负担 |
| ORM | **SQLAlchemy 2.0** | 模型即表结构，改一处同步；与抄来的 Python 参考代码同源 |
| 迁移 | **Alembic** | 表结构变更可追溯，避免手改线上库 |
| 校验 | **Pydantic v2** | 一份模型同时管校验、序列化、接口文档 |
| 数据库 | **MySQL 8**（或 PostgreSQL） | 国内运维熟悉，云厂商支持好 |
| 前端 | **Vue 3 + Vite + Element Plus** | 中文资料最多，表格/表单/弹窗开箱即用 |
| 状态管理 | **Pinia** | Vue 3 官方推荐 |
| 部署 | **Docker Compose** | 一台机器起全套 |

**为什么是这套：**

1. **轻**。FastAPI 不需要 Spring 那套多模块 + 依赖注入 + 一堆 starter，一个 `main.py` 就能跑起来。依赖清单通常不超过 10 个包。
2. **好改**。Python 动态语言，改字段、加状态、调逻辑都是改一处；Pydantic 的校验规则和 API 文档是同一份定义，不用维护两遍。
3. **联调快**。FastAPI 自带 `/docs`（Swagger UI），前端直接照着点，不用手写接口文档。
4. **前端省事**。Element Plus 的 `el-table` / `el-form` / `el-dialog` 覆盖了后台管理 90% 的场景，抄来的页面改改就能用。
5. **数据处理**。这类系统免不了 Excel 导入导出，Python 的 `openpyxl` / `pandas` 最省事。

### 替代方案

| 情况 | 换成 |
|---|---|
| 团队是 JS/TS 为主 | NestJS + Prisma + Vue3（同语言，但 NestJS 比 FastAPI 略重） |
| 想全栈一个语言 | Next.js 全栈（好处是省掉前后端分离，坏处是后台管理系统不如 Vue 顺手） |
| 团队 Java 底子厚、想直接用现成系统 | 直接拿若依WMS 改（不算"轻"，但有完整可运行基础，改起来有参照） |

### 明确不推荐

**yudao 那一整套**（Spring Cloud + Flowable + Redis + Redisson + Quartz + SkyWalking…）。
对一个内部用的小系统，这是明显的过度设计。它的价值在于**表结构和业务模型设计**，不在技术栈——抄它的模型，别抄它的架子。

## 二、抄取清单

| 抄什么 | 从哪抄 | 具体内容 |
|---|---|---|
| **主从表结构** | yudao `yudao-module-erp` | `erp_sale_order` + `_items`、`erp_purchase_order` + `_items`、`erp_sale_out` + `_items`、`erp_purchase_in` + `_items` 的主表存汇总、明细存 SKU 数量的范式 |
| **库存双表模型** | yudao `yudao-module-wms` | `wms_inventory`（余额，唯一键 `sku_id + warehouse_id`）+ `wms_inventory_history`（流水，记 `before_quantity` / `after_quantity` / 关联单号 / 单价金额） |
| **库存并发控制** | yudao `WmsInventoryServiceImpl.changeInventory()` | 批量 `SELECT ... FOR UPDATE` 一次锁定（不要逐行加锁，会死锁）+ 库存行懒创建 + 捕获 `DuplicateKeyException` 后重查 |
| **部分入库/出库** | yudao ERP | 订单项带 `in_count` / `out_count`，每次入库累加、不超过订单总量。避免"一次没到齐就废单" |
| **单据状态机** | 若依WMS | 单据三态：`暂存 → 完成 / 作废`。简单清晰，前端状态管理可复用 |
| **审批状态** | yudao ERP | `ErpAuditStatus`：未审批 / 已审批。**审批动作才影响库存**，订单本身不碰库存 |
| **角色划分** | procureflow | admin / buyer / approver / **warehouse** 四角色，权限边界清晰，正好对上"运营 / 仓储" |
| **后端工程结构** | procureflow | 每个业务域一个独立包（models + routes + schemas + service），统一响应体 + 统一异常处理。整个骨架不到 7KB |
| **单据打印** | 若依WMS | 网页打印入库单 / 出库单 |
| **移库单** | yudao `yudao-module-wms` 的 `wms_transfer` + 若依WMS「移库」 | 出库仓 → 入库仓的单据化调拨；单据与库存分离，只有「执行移库」才动库存（五阶段已落地） |
| **盘库单** | yudao `yudao-module-wms` 的 `wms_stock_take` + 若依WMS「盘库」 | 建单快照账面 → 录入实盘 → 完成时按差异调库存（五阶段已落地） |
| **库存预警** | `vvsgxmn/WarehouseManage` | SKU 上维护安全库存下限 `min_stock`，可用量低于下限即预警（五阶段已落地） |

## 三、数据模型

### 基础数据层

| 表 | 关键字段 |
|---|---|
| `warehouse` | id, name, code, address, status |
| `product` | id, name, category_id, brand, unit, status |
| `product_sku` | id, product_id, sku_code, spec, price, weight |

### 库存层

**`inventory`** — 库存余额

| 字段 | 类型 | 说明 |
|---|---|---|

## 四、状态机

### 销售订单（协作状态）—— 必须自己写

```
待接单(10) ──仓储接单──> 已接单(20) ──开始备货──> 备货中(30)
   │                        │                        │
   │                        │                  ┌─────┴─────┐
   │                        │                  │           │
   │                        │              库存充足    库存不足
   │                        │                  │           │
   │                        │                  │      发起采购
   │                        │                  │      （子流程）
   │                        │                  │           │
   │                        └──────────────────┴───────────┘
   │                                     │
   │                                  拣货出库
   │                                     ↓
   └──取消(90)<──────────────      已发货(40) ──运营确认──> 已完成(50)
```

| 值 | 状态 | 谁操作 | 说明 |
|---|---|---|---|
| 10 | 待接单 | 运营 | 提交后进入订单池 |
| 20 | 已接单 | 仓储 | 认领，同时写入 `claimed_by` / `claimed_at` |
| 30 | 备货中 | 仓储 | 库存够就直接拣货；不够则发起采购 |
| 40 | 已发货 | 仓储 | **回传点**：写物流单号，状态同步给运营 |
| 50 | 已完成 | 运营 | 确认收货，归档 |
| 90 | 已取消 | 运营/仓储 | 需记录取消原因 |

### 出库单状态 —— 抄若依WMS

```
草稿(10) ──完成──> 已完成(20)
   └──作废──> 已作废(90)
```

只有草稿可编辑/删除；完成时触发库存扣减；作废不影响库存。

### 采购单状态 —— 抄 yudao ERP

```
未审批(0) ──审批──> 已审批(1)
```

采购订单审批**不影响库存**；采购入库审批**才增加库存**，反审批则回退。

## 六、必须自己写的部分

这些是开源项目里**都没有**的，别指望能抄到：

1. **协作状态机**（第四节）。所有开源项目要么是纯 WMS（只有单据态），要么是标准 ERP（只有审批态），没有"运营推单 → 仓储认领"这条链。
2. **订单池的可见性规则**。运营只能看自己创建的单，仓储能看全部待接单的。这是数据权限，不是普通 RBAC 菜单权限能覆盖的。
3. **状态回写与通知**。仓储改状态后，运营端要能立刻看到。轻量做法是前端轮询（30 秒一次），重一点上 WebSocket。
4. **库存不足触发采购的判断逻辑**。备货时校验 `inventory.quantity`，不足则生成采购单并挂到该订单下。
5. **库存预留**。yudao WMS 没有预留机制，两个草稿出库单会抢同一批货。建议在 `inventory` 加 `reserved_quantity` 字段，接单时预留、发货时转实扣、取消时释放。

## 七、落地步骤

**第一阶段：跑通主链路（骨架）**
1. 起 FastAPI + MySQL + Vue3 项目骨架
2. 建基础数据表（仓库、商品、SKU、往来单位、用户角色）
3. 建 `sales_order` + `sales_order_item`，实现运营下单 + 订单列表
4. 实现仓储接单 → 发货 → 状态回传
5. 前端两个视图：运营端（我的订单）、仓储端（待接单 + 待发货）

**第二阶段：加库存**
6. 建 `inventory` + `inventory_history`，实现库存变更服务（抄 yudao 的批量悲观锁方案）
7. 出库单完成时扣减库存，写流水
8. 库存查询页 + 流水页

**第三阶段：加采购**
9. 建采购单 + 采购入库
10. 备货时库存不足 → 生成采购单
11. 采购入库 → 库存增加 → 订单自动回到备货中

**第四阶段：补齐**
12. 库存预留机制
13. 单据打印（抄若依WMS 的网页打印）
14. 消息通知（订单状态变更提醒）
15. Excel 导入导出
