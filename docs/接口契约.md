## 二、统一响应格式

**所有接口**（含错误）统一返回：

```json
{
  "code": 0,
  "msg": "ok",
  "data": {}
}
```

| code | 含义 |
|---|---|
| 0 | 成功 |
| 400 | 参数错误 |
| 401 | 未登录 / token 失效 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |
| 1001 | 业务错误（如状态流转不合法），msg 为具体原因 |

分页响应 `data` 结构：

```json
{
  "list": [],
  "total": 100,
  "page": 1,
  "page_size": 20
}
```

分页请求统一用 query 参数：`?page=1&page_size=20`。

| 发货 | 30 | 40 | warehouse / admin |
| 确认完成 | 40 | 50 | operator（本人）/ admin |
| 取消 | 10 / 20 / 30 | 90 | operator（本人）/ warehouse / admin |

> 以下章节是第一阶段契约的**增量补充**，第一至八节仍然有效。

## 九、二阶段：库存与出库单

### 9.1 设计说明

一阶段的「发货」接口在二阶段**增强**为真实库存操作。`POST /api/warehouse/orders/{id}/ship` 被调用后，后端依次执行：

1. 校验库存是否充足（不足返回 `code=1001`，提示缺哪个 SKU、缺多少）
2. 批量扣减库存 + 写库存流水（同一事务）
3. 自动生成一张**已完成**的出库单（`sales_out`），作为发货凭证
4. 订单转「已发货」，回写明细 `out_count`

**前端不需要改动发货接口的调用方式**，只是后端内部行为变重了。

### 9.3 库存变更服务（共享，采购模块也要调用）

所有库存变动**必须**走这个统一入口，禁止在业务代码里直接 UPDATE 库存表。

```python
def change_inventory(
    db,                     # Session
    changes: list[dict],    # [{"sku_id": 1, "warehouse_id": 1, "quantity": 10}]  正数入库，负数出库
    order_no: str,          # 关联单号
    order_type: str,        # SALES_OUT / PURCHASE_IN / ADJUST
    operator_id: int,       # 操作人
) -> None
```

实现要求（严格按此，这是抄 yudao WMS 的核心）：

1. **去重合并**：同一个 `(sku_id, warehouse_id)` 出现多行时，先在内存里合并成一个变更量，减少数据库交互
2. **懒创建**：库存行不存在时，先尝试插入 `quantity=0` 的记录，捕获 `IntegrityError` 后重新查询。**不要"先查后插"**（有竞态）
3. **批量悲观锁**：收集所有待锁定的库存行 id，一次性 `SELECT ... FOR UPDATE` 锁定。**禁止在循环里逐行加锁**（会死锁）
4. **校验**：出库时校验 `quantity - reserved_quantity >= 出库量`，不足抛业务异常，错误信息必须带 SKU 编码、仓库名、当前可用量、需求量
5. **更新 + 写流水**：更新库存，同时为每笔变动写 `inventory_history`（记 `before_quantity` / `after_quantity`）

## 十、三阶段：采购

### 10.1 设计说明

备货时若库存不足，仓储端可发起采购：

# 四阶段契约（库存预留 / 打印 / 导入导出）

## 十二、库存预留机制

### 12.1 要解决的问题

当前实现里，**创建订单时不预扣库存，只在发货时才扣**。这意味着两张待发货的订单可以同时"看到"同一批货，先发货的成功，后发货的才失败——对仓储端来说是很差的体验（货都拣好了才发现不够）。

### 12.2 方案

`inventory.reserved_quantity` 字段（第一阶段就建好了，一直没用）投入使用：

| 时点 | 库存操作 |
|---|---|
| 仓储接单（status 10 → 20） | **预留**：`reserved_quantity += 需求量`，`quantity` 不变 |
| 发货（status 30 → 40） | **转实扣**：`reserved_quantity -= 需求量`，同时 `quantity -= 需求量`，写流水 |
| 订单取消（status → 90，且已接单） | **释放**：`reserved_quantity -= 需求量` |
| 出库单作废 | **回滚实扣**：`quantity += 需求量`（预留早在发货时就释放了，此处不再动 `reserved_quantity`） |

**可用量定义**：`available_quantity = quantity - reserved_quantity`

**接单时校验**：`available_quantity >= 需求量`，不足则返回 `code=1001`，msg 说明哪个 SKU 在哪个仓库可用量不足、缺多少。

### 12.3 服务层新增两个函数

在 `app/services/inventory_service.py` 里新增（与既有 `change_inventory` 同级）：

```python
def reserve_inventory(db, changes, order_no, operator_id) -> None
    """预留库存：只增加 reserved_quantity，不改 quantity，不写库存流水（预留不是库存变动）。"""

def release_inventory(db, changes, order_no, operator_id) -> None
    """释放预留：减少 reserved_quantity。释放量不得使 reserved_quantity 为负。"""
```

实现要求与 `change_inventory` 一致：去重合并、懒创建（savepoint 兜并发）、**批量** `SELECT ... FOR UPDATE` 加锁、校验后更新。**内部不 commit**，由调用方统一提交。

### 12.4 受影响的既有接口（行为增强，请求/响应格式不变）

| 接口 | 变化 |
|---|---|
| `POST /api/warehouse/orders/{id}/claim` | 接单前校验可用量，接单时执行预留；可用量不足返回 `code=1001` |
| `POST /api/warehouse/orders/{id}/ship` | 发货时先释放预留，再执行实扣 + 写流水（同一事务） |
| `POST /api/sales-orders/{id}/cancel` | 若订单处于已接单（20）或备货中（30），取消时释放预留 |
| `POST /api/sales-outs/{id}/cancel` | 作废时回滚实扣的库存（`quantity +=`），不动 `reserved_quantity` |

# 六阶段：订单模型重构（运营录入模式）

> **本章是对前面章节的覆盖性变更**，冲突处以本章为准。

## 十六、背景与变更概览

### 16.1 为什么要改

原设计：运营从系统内的 SKU 库选商品下单。
实际业务：运营在**外部平台**接到订单，需要把订单信息录入系统。商品可能是从没卖过的新品，系统里还没有对应货号。

### 16.2 新流程

```
运营录入订单（订单号 + 多行商品，每行：商品名 + 货号或勾选新品 + 数量 + 预计成本）
   ↓ 提交前弹窗二次确认数量
仓库接单
   ↓
逐行处理货号：
   · 填了货号的行  → 按货号匹配系统里的 SKU，回填关联
   · 勾了新品的行  → 仓库新建货号（创建 SKU）并关联到该订单行
   ↓ 全部行关联完成，才允许进入备货
按数量查库存：
   · 库存够 → 发货（扣库存 + 生成出库单）
   · 库存不够 → 发起采购（采购价不得高于运营填的预计成本）→ 收货入库 → 发货
```

### 16.3 三条硬规则

1. **货号与新品二选一**：每个订单行必须「填了货号」或「勾选新品」，不能都填也不能都不填
2. **关联后锁定**：订单行的货号一旦由仓库关联成功，运营端不可再修改
3. **采购价上限**：因某订单缺货而发起的采购，采购单价**不得高于**该订单行运营填写的预计成本

---

## 十七、数据模型变更

### 17.1 `sales_order` 变更

| 字段 | 变更 | 说明 |
|---|---|---|
| `no` | **语义变更** | 改为**运营录入的订单号**（外部平台单号），仍保持唯一索引 |
| `customer_id` | **删除** | 不再需要客户字段 |
| `total_price` | **语义变更** | 改为各明细行 `expect_price × count` 的汇总（预计总成本） |
| 其余字段 | 不变 | `status` / `audit_status` / `warehouse_id` / `claimed_by` / `claimed_at` / `prepare_at` / `shipped_at` / `finished_at` / `express_no` / `cancel_reason` / `remark` / `created_by` 均保留 |

### 17.2 `sales_order_item` 变更

| 字段 | 变更 | 说明 |
|---|---|---|
| `product_name` | **新增** | 商品名，自由文本，`varchar(200)`，**必填** |
| `sku_code` | **新增** | 货号，`varchar(64)`，**选填**；与 `is_new` 互斥 |
| `is_new` | **新增** | 是否新品，`tinyint`，默认 0；与 `sku_code` 互斥 |
| `sku_id` | **改为可空** | 原为必填；由仓库关联货号后回填。**为空表示尚未关联** |
| `expect_price` | **新增**（替代原 `price`） | 运营填写的**预计成本单价**，`decimal(14,2)`，必填，需 > 0 |
| `total_price` | **语义变更** | = `count × expect_price` |
| `count` / `out_count` | 不变 | |

**校验规则（创建订单时）**：

- `product_name` 不能为空
- `sku_code` 与 `is_new` **必须二选一**：填了货号就不能勾新品，勾了新品就不能填货号
- `count` > 0
- `expect_price` > 0
- 同一订单内 `sku_code` 不允许重复

### 17.3 `purchase_order_item` 新增约束

采购价 `price` **不得高于**所关联销售订单行的 `expect_price`。

- 校验时机：**创建采购单**时（仅当采购单关联了 `sales_order_id`）
- 匹配方式：按 `sku_id` 找到该销售订单下对应的订单行，取其 `expect_price` 作为上限
- 超出时返回 `code=1001`，msg 说明：「SKU001 的采购价 15.00 高于运营填写的预计成本 12.00」

## 十八、状态机变更

订单主状态在原有基础上**新增一个状态值 25「数量待确认」**：

| 值 | 状态 | 谁触发 | 说明 |
|---|---|---|---|
| 10 | 待接单 | 运营下单 | 订单进入后台订单池 |
| 20 | 已接单 | 仓储接单 | 写 `claimed_by` / `claimed_at` / `warehouse_id`；此阶段处理货号关联 |
| **25** | **数量待确认** | **系统自动**（仓储绑完所有货号后） | 等运营填写并确认最终数量 |
| 30 | 备货中 | **运营确认数量后自动** | 仓储开始备货；库存不足时由仓储采购处理 |
| 40 | 已发货 | 仓储发货 | 状态回传点 |
| 50 | 已完成 | 运营确认 | |
| 90 | 已取消 | 运营 / 仓储 | |

**流转规则**：

```
待接单(10) ──仓储接单──▶ 已接单(20) ──绑完所有货号（自动）──▶ 数量待确认(25)
                                                                    │
                                                          运营填写并确认数量
                                                                    ▼
                                                              备货中(30)
                                                                    │
                                                              仓储发货
                                                                    ▼
                                                              已发货(40) ──运营确认──▶ 已完成(50)
```

- **10 → 20**：仓储调用 `claim`
- **20 → 25**：仓储调用 `bind-sku`，且**该订单所有明细行的 `sku_id` 都已绑定**时，系统自动流转（不需要额外调用接口）
- **25 → 30**：运营调用 `confirm-quantity`（见 19.6）
- **30 → 40**：仓储调用 `ship`
- **40 → 50**：运营调用 `confirm`
- **取消**：`status` 为 10 / 20 / 25 / 30 时可取消，转为 90

**废弃的接口**：原 `POST /api/warehouse/orders/{id}/prepare`（20→30 的路径）**不再使用**，`25 → 30` 由运营确认触发。该接口保留但调用会返回 `code=1001` 提示流程已变更，或直接从前端移除入口。

### 18.1 库存处理时点（重要）

运营确认数量不校验或预留库存；库存不足由仓储在备货阶段采购处理：

| 时点 | 库存操作 |
|---|---|
| 接单 `claim`（10→20） | 不校验、不预留 |
| 绑定货号 `bind-sku` | 不预留 |
| **运营确认数量（25→30）** | 更新最终数量与订单汇总，**不校验、不预留库存** |
| 备货中（30） | 仓储检查库存，库存不足则走采购流程 |
| 发货 `ship`（30→40） | 校验实际库存后实扣并写库存流水 |
| 取消订单 `cancel` | 不调整库存 |
| 作废出库单 | 回滚已实扣的库存 |

> 一句话原则：**运营确认订单需求，仓储负责库存与采购；只有实际发货会扣库存。**

## 十九、接口变更

### 19.1 `POST /api/sales-orders`（请求体重构）

**请求**：

```json
{
  "no": "TB20260917001",
  "remark": "加急",
  "items": [
    { "product_name": "蓝牙耳机", "sku_code": "HW-001", "count": 2, "expect_price": 35.00 },
    { "product_name": "手机壳", "is_new": 1, "count": 5, "expect_price": 8.50 }

}
```

**规则**：

- `no` 必填，**全局唯一**，重复时返回 `code=1001`「订单号已存在：TB20260917001」
- `items` 至少一行
- 每行的 `sku_code` / `is_new` 二选一（见 17.2 校验规则）
- `total_count` / `total_price` 由后端按明细汇总，不信任前端
- 初始 `status = 10`
- `created_by` 取当前登录用户

**响应**：订单详情对象（见 19.4）

### 19.2 `POST /api/warehouse/orders/{id}/bind-sku`（新增）

仓储端为订单明细行关联或创建货号。

**请求**：

```json
{
  "items": [
    { "item_id": 1, "sku_code": "HW-001" },
    { "item_id": 2, "new_sku": { "sku_code": "HW-002", "product_name": "手机壳", "spec": "透明", "price": 8.50 } }
  ]
}
```

**两种模式**（每个 item 二选一）：

| 模式 | 字段 | 行为 |
|---|---|---|
| 关联已有 | `sku_code` | 按货号查找系统里的 SKU，回填 `sku_id`；找不到返回 `code=1001`「货号 HW-001 在系统中不存在，请改为新建」 |
| 新建 | `new_sku` | 创建 Product（若同名商品不存在）+ SKU，然后回填 `sku_id`；`sku_code` 重复时返回 `code=1001` |

**规则**：

- 仅 `warehouse` / `admin` 可调用
- 订单状态必须是 20（已接单），否则 `code=1001`
- 只能操作该订单下的明细行，`item_id` 不属于该订单时 `code=1001`
- 已关联过的行（`sku_id` 不为空）**不允许再次修改**，返回 `code=1001`「该商品已关联货号，不可修改」—— 这条对应「关联后运营禁止修改」的约束，仓储端同样锁死
- 支持**部分关联**：可以一次只关联一部分行，多次调用直到全部关联完成
- 全部关联完成后，返回的订单详情里 `all_sku_bound = true`

### 19.3 `POST /api/warehouse/orders/{id}/prepare`（新增校验）

在原有状态校验（必须为 20）基础上，新增：

### 19.6 `POST /api/sales-orders/{id}/confirm-quantity`（新增）

运营确认数量，订单从「数量待确认」(25) 流转到「备货中」(30)。

**请求**：必须完整提交订单的每一条明细；`item_id` 不可重复，`count` 必须是大于 0 的整数。

```json
{
  "items": [
    { "item_id": 101, "count": 8 },
    { "item_id": 102, "count": 3 }
  ]
}
```

**规则**：

- 仅 `operator`（且只能操作自己创建的订单）/ `admin` 可调用
- 订单 `status` 必须为 **25**，否则返回 `code=1001`，msg 说明当前状态，例如「订单当前状态为「已接单」，无法执行确认数量操作」
- `items` 必须恰好覆盖这张订单的全部明细；缺少、重复或包含其他订单的明细均返回 `code=1001`
- 运营可修改每一行的最终出库数量；后端按提交值重算明细小计、订单总数量和预计总成本
- 成功后的处理（同一事务）：更新明细数量/小计及订单总数量/预计总成本，`status` → 30，并写 `prepare_at`
- **不校验、不预留库存**。库存不足由仓储在备货阶段采购处理；实际发货时才校验可用库存，库存不足时发货失败且订单保持 30
- 响应：订单详情对象

> 这个接口负责状态流转（25→30）与最终数量确认；原先由仓储触发的 `prepare` 接口不再使用。

### 19.7 `bind-sku` 的补充行为

`bind-sku` 在**本次调用完成后该订单所有明细行的 `sku_id` 均不为空**时，除了返回订单详情，还要把订单 `status` 从 20 自动流转到 **25**（数量待确认）。这是契约 18 里「20 → 25 系统自动流转」的落地点。

- 支持部分关联：一次只绑一部分时，状态保持 20
- 绑定完成后返回的详情里 `status` 应为 25、`all_sku_bound` 为 true

## 十六、移库单（库存调拨）

### 16.1 设计说明

- 一张移库单 = **一个出库仓 → 一个入库仓**，一次可移多个 SKU
- 两阶段状态机（抄 yudao WMS 单据风格）：`草稿(10) → 已完成(20)`；仅草稿可作废 `(90)`
- **只有「执行移库」才动库存**。建单本身不动库存（与采购单同样的设计：单据与库存分离）
- 执行移库在同一事务里：出库仓 `-count`（流水 `TRANSFER_OUT`）、入库仓 `+count`（流水 `TRANSFER_IN`），共写 2×N 条流水
- 出库仓库存不足 → 整体失败，`code=1001`，msg 带 SKU 编码 / 仓库名 / 可用量 / 需求量

### 16.2 新增表

**`stock_transfer` 移库单主表**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint | 主键，自增 |
| no | varchar(32) | 单号 `TR` + yyyyMMdd + 4 位当日流水，**唯一** |
| from_warehouse_id | bigint | 出库仓 `warehouse.id` |
| to_warehouse_id | bigint | 入库仓 `warehouse.id` |
| status | tinyint | 10 草稿 / 20 已完成 / 90 已作废 |
| total_count | decimal(14,2) | 合计移库数量 |
| remark | varchar(500) | 备注，可空 |
| created_by | bigint | 制单人 `sys_user.id` |
| finished_at | datetime | 执行移库时间，可空 |
| created_at / updated_at | datetime | 统一时间戳 |

索引：`no` 唯一索引；`status`、`from_warehouse_id`、`to_warehouse_id` 普通索引。

**`stock_transfer_item` 移库单明细**

| 字段 | 类型 | 说明 |

| GET | `/api/stock-transfers/{id}` | warehouse, admin | 详情（含明细） |

**POST `/api/stock-transfers` 请求**

## 十七、盘点单（盘库）

### 17.1 设计说明

- 抄 yudao WMS 的盘库单：建单 → 录入实盘 → 完成盘点按差异调整库存
- 建单时选定仓库 + SKU 清单，**自动快照账面数量**（`inventory.quantity`）
- 「完成盘点」时按 `差异 = 实盘 - 账面` 走 `change_inventory`（`order_type = STOCK_TAKE`）
- 状态：`10 盘点中 / 20 已完成 / 90 已作废`；仅「盘点中」可录入实盘、完成、作废
- 与既有 `POST /api/inventory/adjust` 的关系：`adjust` 是**单点即时调整**（无单据），
  盘点单是**成批、有单据留痕**的流程。两者都走 `change_inventory`，互不替代。
- **账面快照与完成时实际库存可能不一致**（盘点期间发生了出入库）。本阶段约定：
  以「快照账面」为基准计算差异并落流水，不做二次校验；`diff_count` 记录该次盘点的差异合计。

### 17.2 新增表

**`stock_take` 盘点单主表**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint | 主键，自增 |
| no | varchar(32) | 单号 `ST` + yyyyMMdd + 4 位当日流水，**唯一** |
| warehouse_id | bigint | 盘点仓库 `warehouse.id` |
| status | tinyint | 10 盘点中 / 20 已完成 / 90 已作废 |
| total_count | decimal(14,2) | 账面数量合计（建单时快照） |
| diff_count | decimal(14,2) | 差异合计（实盘 - 账面），完成时写入，未完成时 0 |
| remark | varchar(500) | 备注，可空 |
| created_by | bigint | 制单人 `sys_user.id` |
| finished_at | datetime | 完成盘点时间，可空 |
| created_at / updated_at | datetime | 统一时间戳 |

索引：`no` 唯一索引；`warehouse_id`、`status` 普通索引。

**`stock_take_item` 盘点单明细**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint | 主键，自增 |
| stock_take_id | bigint | 关联 `stock_take.id` |
| sku_id | bigint | 关联 `product_sku.id` |
| book_quantity | decimal(14,2) | 账面数量（建单快照） |
| actual_quantity | decimal(14,2) | 实盘数量，建单时 = 账面数量 |
| diff_quantity | decimal(14,2) | 差异 = 实盘 - 账面，完成时写入 |
| remark | varchar(255) | 行备注（如「破损 2 件」），可空 |
| created_at / updated_at | datetime | 统一时间戳 |

索引：`stock_take_id` 普通索引。

### 17.3 新增接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/stock-takes` | warehouse, admin | 新建盘点单 |
| GET | `/api/stock-takes` | warehouse, admin | 列表，支持 `?page=&page_size=&keyword=&status=&warehouse_id=` |
| GET | `/api/stock-takes/{id}` | warehouse, admin | 详情（含明细） |
| PUT | `/api/stock-takes/{id}/items` | warehouse, admin | 录入实盘数量 |
| POST | `/api/stock-takes/{id}/finish` | warehouse, admin | 完成盘点（按差异调库存） |
| POST | `/api/stock-takes/{id}/cancel` | warehouse, admin | 作废 |

`keyword` 匹配：单号 / 备注。

**POST `/api/stock-takes` 请求**

```json
{
  "warehouse_id": 1,
  "remark": "月末盘点",
  "sku_ids": [1, 2, 3]
}
```

- `sku_ids` 不传或为空数组 → 取该仓库**所有已有库存记录的 SKU**（`inventory` 表里 `warehouse_id` 匹配的行）
- 该仓库没有任何库存记录且未指定 `sku_ids` → `code=1001`「该仓库没有库存记录，无法建盘点单」
- 指定了不存在的 SKU → `code=1001`
- `book_quantity` 取建单时的 `inventory.quantity`（无库存行则记 0）
- `total_count` = 所有行账面数量合计

**PUT `/api/stock-takes/{id}/items` 请求**

```json
{
  "items": [
    { "item_id": 1, "actual_quantity": 98, "remark": "破损 2 件" },
    { "item_id": 2, "actual_quantity": 5 }
  ]
}
```

- 仅 `status = 10` 可录入，否则 `code=1001`
- `actual_quantity >= 0`（Pydantic `ge=0`，违规 `code=400`）
- `item_id` 必须属于该盘点单，否则 `code=1001`「盘点明细不存在」
- 同一 `item_id` 不允许重复行（Pydantic 层，`code=400`）
- 允许部分录入（只传部分行），未传的行保持原值

**POST `/api/stock-takes/{id}/finish`**

- 仅 `status = 10` 可完成，否则 `code=1001`
- 逐行算 `diff = actual_quantity - book_quantity`；`diff != 0` 的行才走 `change_inventory`（`order_type = STOCK_TAKE`，单号作业务单号）
- 差异为负时校验可用量，不足 → `code=1001`（理论上不该发生，作兜底）
- 写回每行 `diff_quantity`；主表 `diff_count` = 差异合计、`status = 20`、`finished_at`
- 全部差异为 0 时也允许完成（不写流水），`diff_count = 0`

**POST `/api/stock-takes/{id}/cancel`**

- 仅 `status = 10` 可作废，否则 `code=1001`
- 不动库存

**响应结构（详情）**

```json
{
  "id": 1,
  "no": "ST202609160001",
  "warehouse_id": 1,
  "warehouse_name": "主仓",
  "status": 10,
  "status_text": "盘点中",
  "total_count": 300.00,
  "diff_count": 0.00,
  "remark": "月末盘点",
  "created_by": 3,
  "created_by_name": "仓管老李",
  "finished_at": null,
  "created_at": "2026-09-16 20:00:00",
  "updated_at": "2026-09-16 20:00:00",
  "items": [
    {
      "id": 1,
      "stock_take_id": 1,
      "sku_id": 1,
      "sku_code": "SKU001",
      "product_name": "商品A",
      "spec": "红色/大号",
      "book_quantity": 100.00,
      "actual_quantity": 100.00,
      "diff_quantity": 0.00,
      "remark": null
    }
  ]
}
```

列表元素 = 详情去掉 `items`。`status_text` 映射：`10 盘点中 / 20 已完成 / 90 已作废`。

## 十八、库存预警（安全库存）

### 18.1 设计说明

抄 `vvsgxmn/WarehouseManage` 的库存预警：在 SKU 上维护安全库存下限，
**可用量低于安全库存**即进入预警列表。

`available_quantity = quantity - reserved_quantity`（沿用第十二节定义）。

### 18.2 表变更：`product_sku` 新增列

| 字段 | 类型 | 说明 |
|---|---|---|
| min_stock | decimal(14,2) | 安全库存下限，`NOT NULL DEFAULT 0.00`；**0 表示不预警** |

`product_sku` 的请求 / 响应 schema（`SkuCreate` / `SkuUpdate` / SKU 序列化）都要带上 `min_stock`：
- `SkuCreate.min_stock`：`Decimal`，`ge=0`，默认 `0.00`
- `SkuUpdate.min_stock`：`Decimal | None`，`ge=0`
- SKU 列表 / 详情 / 下拉选项的响应里都返回 `min_stock`（float）

### 18.3 新增接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/inventory/alerts` | operator, warehouse, admin | 库存预警列表 |

- 支持 `?page=&page_size=&warehouse_id=`
- 筛选条件：`min_stock > 0 AND (quantity - reserved_quantity) < min_stock`
- 排序：短缺量从大到小
- 响应元素 = 库存列表元素（`inventory_out`）额外加：

| 字段 | 说明 |
|---|---|
| `min_stock` | SKU 的安全库存下限 |
| `shortage` | 短缺量 = `min_stock - available_quantity`，恒 > 0 |

> 注意路由注册顺序：`/api/inventory/alerts` 必须与 `/api/inventory/history` 一样是**静态路径**，
> 现有 `/api/inventory` 下没有 `/{id}` 通配路由，因此不冲突。

### 18.4 前端

- 「库存管理」菜单下新增「库存预警」页：表格 + 仓库筛选 + 分页，短缺量高亮
- SKU 管理的新增 / 编辑表单加「安全库存」输入框（数字，≥ 0，默认 0）
- SKU 列表加「安全库存」列
- 首页看板加一张「库存预警」统计卡（预警条数），点击跳转预警页

## 二十、五阶段数据流小结

```
移库：建单(草稿,10) ──执行移库──▶ 出库仓 -N / 入库仓 +N ──▶ 已完成(20)
                                  （TRANSFER_OUT + TRANSFER_IN 两条流水）
      草稿 ──作废──▶ 已作废(90)（不动库存）

盘点：建单(盘点中,10，快照账面) ──录入实盘──▶ ──完成盘点──▶ 按差异调库存 ──▶ 已完成(20)
                                                        （STOCK_TAKE 流水）
      盘点中 ──作废──▶ 已作废(90)（不动库存）

预警：product_sku.min_stock > 0 且 可用量 < min_stock ──▶ /api/inventory/alerts
```
