## 补充调研：MySQL 原生的开源 WMS（修正纪要结论）
用户追问「GitHub 上没有用 MySQL 的吗」。核查后确认：**纪要第 8.5/9 节「Python 生态里没有 MySQL 原生的成熟 WMS」的说法不成立**，存在反例。

| 项目 | 栈 | 数据库 | 许可 | 最近更新 |
|---|---|---|---|---|
| shuxiang/MT-WMS（71★） | Python / Flask + SQLAlchemy | **MySQL 原生**（`settings_local.py` 默认 `mysql+pymysql://`） | Apache-2.0 | 2025-05 |
| inventree/InvenTree（7.5k★） | Python / Django | **官方支持 MySQL**（`database.engine: mysql`） | MIT | 2026-09（活跃） |
| zccbbg/wms-ruoyi（1.2k★） | Java / SpringBoot | MySQL 原生 | 修改版 Apache-2.0 | 2026-03 |
| lysilver/KopSoftWms（896★） | .NET 9 + SqlSugar | MySQL / SQL Server 双支持 | README 写「仅个人学习，商用需授权」，GitHub 标 MIT（**不一致**） | 2026-06 |
| GreaterWMS/GreaterWMS（4.4k★） | Python / Django | 官方 PG；Django ORM 天然支持 MySQL，但未官方支持 | Apache-2.0 | 2025-09 |
| hightower-systems/sentry-wms（22★） | Python / Flask | PG 硬耦合（80 个手写 SQL + DEFERRABLE 触发器） | Apache-2.0 | 2026-08 |

关键结论：
- **MT-WMS 是最贴合的候选**：Python + Flask + MySQL 原生，支持多仓多货主、波次合并拣货，Apache-2.0，含 Web 前后端（前端 Vue2 + antd-design-vue，另有 PDA/App 未开源）。代价：栈偏老（Flask 2.0.3 / SQLAlchemy 1.4，2022 年建仓），代码基本无封装，文档在作者自建站点。
- **InvenTree 是「被忽略的高质量底座」**：Python/Django、MIT、7.5k★、持续活跃，官方支持 MySQL，含 Part/Stock/StockLocation + 采购单/销售单/退货单（RMA）模型。但定位是「库存/物料管理」而非订单履约 WMS，拣货-打包-发货作业流偏弱。
- **KopSoftWms 许可有陷阱**：README 明确「仅供个人学习使用，商业授权请联系原作者」，与仓库标称 MIT 冲突 → 商用前必须澄清。
- **Django 系项目（GreaterWMS）换 MySQL 的成本远低于 Flask 手写 SQL 的 sentry-wms**——这是纪要里没区分的关键点。

对纪要的影响：第 9 节「推荐 Python」的**代价项可以下调**（不必接受 PG→MySQL 移植），但候选底座需要重排。

## 底座对比：sentry-wms vs GreaterWMS（源码级）
下载 sentry-wms 源码到 `/tmp/wms-research/sentry-wms-main` 检索，GreaterWMS 按文件逐个读。

**sentry-wms**：Flask + SQLAlchemy + PG16；65 张表 / 74 个迁移 / 15 种版本化事件；波次拣货有实现（`wave_pick_orders` + `wave_pick_breakdown`）；独立 packing / shipping 环节；`ship.confirmed` 原生支持拆多包裹；RMA 完整；权限真实实现（ADMIN/USER + `user_page_permissions` 页面级授权）。

**GreaterWMS**：Django 4.1 + DRF + PG13；应用为 asn / dn / stock / binset / binproperty / binsize / cyclecount / goods(+6 属性表) / supplier / customer / driver / capital / payment / staff / warehouse / scanner。
**致命短板**：
- `utils/permission.py` **全部注释掉，`has_permission` 直接 `return True`** —— 权限是空壳
- `dn` 只有 3 个模型（DnList / DnDetail / PickingList），**无波次合并、无独立打包/发货记录**
- **无对外连接层**：无 external_id 映射、无事件总线、无幂等键、无 Webhook
- 前端 Quasar(Vue)，与项目已定的 React 不同栈

**结论：sentry-wms 重合度明显更高**，三个决定性理由 = 有对外连接层 / 前端是 React / 权限真实实现。

**文档中我新提出的关键技术判断**：
1. **货号取号必须用原子语句**：`UPDATE category SET seq_counter = seq_counter + 1 WHERE id = ? RETURNING code_prefix || '-' || seq_counter`，避免 `SELECT MAX()+1` 的并发重号；再加 `sku_code` UNIQUE 兜底。
2. **部署架构建议**：同一个 PG 实例 + 同一个 database，中枢表放独立 **`hub` schema**。理由：同库才能用 FK 保证 `submission_line.item_id → sku.id` 完整、才能在同一事务里「原子取号 + 建 SKU」；独立 schema 让两套迁移体系互不干扰（sentry-wms 的 74 个手写 SQL 只动 `public`），将来拆库也只需导出 `hub`。

### 发现的真实缺陷：适配器与入站映射契约错配

`backend/app/adapters.py` 仍用旧字段名，与 `wms/db/mappings/hub.yaml.template` + `wms/docs/hub-integration.md` 的契约对不上：

| 项 | 契约要求 | 修复前 |
|---|---|---|
| items 信封 `external_id` | `sku_code`（如 `A001-1`） | 中枢内部 UUID |
| items `source_payload` | `sku_code`/`category_id`/`code_status` 必填 | 只有 `sku`/`item_name`/`is_active` |
| SO `source_payload` | `order_no`/`remark`/`lines[{line_no,sku_code,qty}]` | `so_number`/`memo`/`line_items[{item_external_id,...}]` |
| 截单 `status` | 枚举须含 `CANCELLED` | 枚举只有 `OPEN` |

**后果**：`mapping_loader` 的必填/enum 校验直接 422；订单行 `cross_system_lookup` 按 `sku_code` 查 `cross_system_mappings.source_id`，而 items 写进去的是 UUID → 永远 miss（409）。
**为何一直没暴露**：测试全程用 `FakeSentryAdapter`，真实 payload 从未被断言。

### 本轮改动

1. **`adapters.py` 对齐契约**：items 信封改用 `sku_code`、补齐必填字段、`external_version` 用 `promoted_at or created_at`（原来是字符串 `"1"`，`iso_timestamp` 策略解析会失败）；订单行改 `lines[].sku_code`；截单去掉 WMS 侧不存在的 `cancel_reason`；下单前校验「货号/数量非空」，否则抛 `SentryAdapterError`（契合「下单失败不推进状态」）。
2. **`hub.yaml.template`**：`status` 枚举补 `CANCELLED`。
3. **新增 `backend/tests/test_adapter_contract.py`**：直接读 `hub.yaml.template`，按映射里每个字段的 `source_path` 反查适配器真实发出的 payload —— 契约漂移即测试失败，堵住 FakeAdapter 掩盖的盲区。
4. **超时提醒自动化**：扫描逻辑从 router 抽到 `services.scan_timeouts`；`main.py` lifespan 挂后台任务每 5 分钟跑（`TIMEOUT_SCAN_INTERVAL_SECONDS`，0 = 关闭；单次异常不终止循环）；补测试覆盖 1h→责任方、2h→两侧同时、不重复发。

## 第三轮：补仓库端 3 屏（P2 收口）

用户问「距离整个项目完成还差多少」→ 盘点后给出约 65–70%，指出**唯一硬阻塞是仓库端 UI**：`warehouse.py` 的核验/转正/改号/判重/派发接口全在，但 `wms/admin/src` 里**零集成**（grep 无任何匹配），仓库管理员没有任何界面可用。用户指令「仓库端继续，开始吧」。

### 先解决的架构问题：浏览器不能持有 `X-WMS-Token`

admin 前端只走 `/api/*`（同源 cookie 认证 + CSRF）；中枢在 8000 端口、用 `X-WMS-Token` 静态密钥认证。若让前端直连，密钥就会进浏览器 —— 不可接受。

**方案：在 wms 后端加代理层**（`wms/api/routes/admin/admin_hub.py`）：

```
admin 前端 → /api/admin/hub/*（require_auth + page_key `hub-warehouse`）
           → 代理注入 X-WMS-Token → 中枢 /api/v1/warehouse/*
```

- 只转发**白名单路径形状**（精确正则，非前缀匹配，避免被当成任意接口放大器）
- 原样透传中枢状态码与 JSON；未配 token 时返回 503 而非透传 401（便于区分部署问题与权限问题）
- `requests` 本来就在 wms 依赖里，无需新增

### 补的缺口：中枢缺「仓库端货号检索」

改号（change-item）与判重（merge-duplicate）都要先搜到目标货号，但中枢只暴露了运营端版本（`current_ops_user` 认证）。新增 `GET /api/v1/warehouse/catalog/skus/search`（`X-WMS-Token` 认证），与运营端共用查询体 `search_active_skus`。
